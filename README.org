Code for running my Raspberry Pi Pico driven 4k Led Marquee. Literal 4k display consisting of 128x32 pixels.

* Equipment
+ 2x 64x32 pixel LED matrix
  - Powered by 10A 5V PSU
+ Raspberry Pi Pico

* Developer environment

Developing in a Raspberry Pi 400. Initially tried using WSL, but the hassle of USB connection pass through was not ideal when repeatedly connecting and disconnecting the Pico.

** Raspberry Pi 400 impressions

When developing using VSCode and Chromium-browser, the machine quickly get sluggish, likely due to low memory.

* Set up development environment

** Install toolchain

The below was suggested by the co-pilot.
#+BEGIN_SRC bash
sudo pacman -S --needed base-devel cmake git python \
  arm-none-eabi-binutils arm-none-eabi-gcc arm-none-eabi-newlib
#+END_SRC

The Pico SDK is pinned in this repository as a Git submodule. Initialize it
before configuring the firmware:
#+BEGIN_SRC bash
git submodule update --init --recursive
#+END_SRC

For a Pico W build, provide the WiFi credentials at configure time:
#+BEGIN_SRC bash
./build-firmware.sh
#+END_SRC

The script asks for the Pico variant and WiFi credentials when needed. It
passes credentials through the environment and removes its temporary build
directory on exit, so they are not stored in the repository, shell history, or
a persistent CMake cache. The credentials are necessarily embedded in the
resulting firmware image.


* Source code layout

** LED driver

I'm using the Picos built in Programmable IO (PIO) to drive the LEDs. 
The pico-examples project `pio/hub75` has been very slightly adjusted for this setup.
https://github.com/raspberrypi/pico-examples/tree/master/pio/hub75

We have the option to drive the LEDs coupled in series as a single 128x32 display, or we could optimize by driving them as two 64x32 displays in parallell.
The Pico has enough GPIO pins for either option. Sticking with the single display solution first, as it means the example code can be used directly.

The LED driver consists of two components, the PIO part that drive the actual IO pins, and the FIFO filling code that feeds it.

The code for pushing the pixels runs as a separate thread on `core1` in order to avoid rendering hickups when communicating over USB. This will also allow is proper double buffering with more advanced render code on `core0`.

** HUB75 wiring

Connect the Pico GPIOs to the first panel's HUB75 input connector as follows.
The physical pin ordering follows the standard HUB75/HUB75E pinout documented
at https://olympianled.com/guides/led-hub-pinout-diagrams. Verify the connector
orientation and pin 1 marker on the panel before wiring it.

| HUB75 signal | Pico GPIO | Common 2x8 input pin |
|--------------+-----------+----------------------|
| R1           | GP0       | 1                    |
| G1           | GP1       | 2                    |
| B1           | GP2       | 3                    |
| GND          | GND       | 4                    |
| R2           | GP3       | 5                    |
| G2           | GP4       | 6                    |
| B2           | GP5       | 7                    |
| GND          | GND       | 8                    |
| A            | GP6       | 9                    |
| B            | GP7       | 10                   |
| C            | GP8       | 11                   |
| D            | GP9       | 12                   |
| CLK          | GP11      | 13                   |
| LAT/STB      | GP12      | 14                   |
| OE           | GP13      | 15                   |
| GND          | GND       | 16                   |

Logical connector view, looking at the panel input header with pin 1 in the
usual marked corner:

#+BEGIN_SRC text
        HUB75 input
     +----------------+
  1  | R1   |  2  G1  |
  3  | B1   |  4  GND |
  5  | R2   |  6  G2  |
  7  | B2   |  8  GND |
  9  | A    | 10  B   |
 11  | C    | 12  D   |
 13  | CLK  | 14  LAT |
 15  | OE   | 16  GND |
     +----------------+
#+END_SRC

On HUB75E panels, pin 8 is the fifth row-address signal (E) rather than GND.
This firmware drives a 1/16-scan HUB75 panel using A-D and does not provide an
E output.

Use the panel's separate 5 V supply for the LED power and connect its ground
to the Pico ground. Do not power the panel from the Pico. GP10 is unused by
the HUB75 interface.

** On board demos

We can control the board over USB to perform various tasks, such as rebooting the device into BOOTSEL mode. We can leverage this to add on board programs to render to the display too, and allow switching using the WebUSB interface.

|------+--------------------------------------------------------------------------|
| B    | Reset to Bootsel mode                                                    |
| F    | Start Fire demo.                                                         |
| S    | Start Snek game.                                                         |

| I    | Report WiFi connection status and current IP address                     |
| W    | Retry the WiFi connection                                                |
| T*   | Set a line of text (binary form), kept on screen                         |
| O*   | Draw a line of text (binary form) once into the current frame            |
| t*   | Set a line of text (ASCII form), kept on screen                          |
| o*   | Draw a line of text (ASCII form) once into the current frame             |

*** Text commands

There are two interchangeable forms. The ASCII form is meant for typing into a
serial terminal; the binary form is meant for programs.

ASCII, terminated by newline:
#+begin_example
t<x>,<y>,<rrggbb>[,<rrggbb>]:<text>
#+end_example

The first colour is the foreground; the optional second colour paints the
glyph background. Without it the text is drawn transparently over whatever is
already on the panel. Only the *first* colon separates the header from the
text, so the text itself may contain both =,= and =:=.

#+begin_example
t0,0,ff8800:HELLO WORLD
t0,8,00ff00,000040:12:30, READY
o40,16,ffffff:ONE FRAME
#+end_example

Binary, 11 byte header followed by the characters:
#+begin_example
[T|O, x, y, fg_r, fg_g, fg_b, bg_r, bg_g, bg_b, opts, n, chars * n]
#+end_example

=opts= bit 0 paints the background; all other bits are reserved. =n= is at
most 32, keeping the whole command inside the 64 byte packet limit.

=T= and =t= store the line and switch the display to text mode, which keeps up
to 4 lines on screen and redraws them every frame. Lines are keyed by =y=:
sending a new string at the same =y= replaces that row, and sending an empty
string clears it. =C= clears every row.

=O= and =o= instead draw once into the frame currently being built. That is
useful for overlaying text on demo 0 (the bouncing dot), but demos that repaint
the whole panel each frame will immediately erase it.

The bundled font is a C64 character set: uppercase letters, digits and common
punctuation only. Lowercase is folded to uppercase and unsupported characters
become spaces. Each glyph is 8x8, so the panel fits 16 characters across and
4 rows down.

*** Setting text from the LAN

On a Pico W, =tools/marquee-text.py= (Python 3, stdlib only) sends the text
command to the TCP listener on port 4242. Use the =I= command to find the IP.

#+begin_example
tools/marquee-text.py -H 192.168.1.50 "HELLO WORLD"
tools/marquee-text.py -H 192.168.1.50 -x 0 -y 8 -c green -b 000040 "12:30"
tools/marquee-text.py -H 192.168.1.50 --clear "ONLY THIS LINE"
tools/marquee-text.py -H 192.168.1.50 --clear   # blank all text
tools/marquee-text.py -H 192.168.1.50 --clock   # set time, show matrix clock
#+end_example

Set =MARQUEE_HOST= to skip =-H=. Colours take =rrggbb=, =#rrggbb= or a few
names (=white=, =red=, =green=, =blue=, =yellow=, =cyan=, =magenta=,
=orange=). =--once= uses the one-shot =o= form instead of text mode. Each
command is sent on its own connection, because the firmware handles only the
first command in each received TCP segment.

WiFi connection progress and errors are logged on the hardware UART using
GP16 (TX), GP17 (RX), 115200 baud, 8-N-1. Commands =I= and =W= work over this
UART as well as USB CDC and WebUSB. A reconnect attempt blocks command handling
for up to 30 seconds while the CYW43 driver searches for the configured SSID.

*** Sine scroller

=R= starts a C64-style sine scroller: the text enters on the right and every
pixel column rides a rolling sine wave. =r= sets the colour and text, then
starts it. Like =t= it is a newline-terminated ASCII line, so it works over
the UART too:

#+begin_example
rffcc00:HELLO FROM THE C64!
r:NEW TEXT, SAME COLOUR
r00ff00:
#+end_example

An empty colour or text keeps the current one. The text may be up to 128
characters and may contain =:=. =tools/marquee-text.py --scroll= sends it:

#+begin_example
tools/marquee-text.py -H 192.168.1.50 --scroll -c cyan "HELLO FROM THE C64 "
#+end_example

*** Morphing clock

=D= shows the local time (HH:MM:SS) in large stroked digits that fill the
panel on a black background. Each digit is drawn as four cubic Bezier
segments, and when a digit changes its control points are blended into the
new digit's over 750 ms. The colour drifts slowly: red, green and blue each
swing between 20% and 70% brightness on their own period (23, 37 and 53
seconds). Until the clock has been set it shows dashes, which morph into the
time once it is known. The time comes from the same sources as the Matrix
clock below.

*** Matrix clock

=M= shows green Matrix-style rain with the local time (HH:MM:SS, C64 font)
slowly drifting just below the centre of the panel. Until the clock has been
set it shows =--:--:--=.

The time comes from two sources:

- *SNTP* (Pico W): once WiFi is up the firmware queries =pool.ntp.org= and
  then re-syncs every hour. Override the server with =-DNTP_SERVER=host=.
- *The =k= command* (any board, any transport): =k1791201594.250= followed by a
  newline sets UTC to that Unix time. =tools/marquee-text.py --clock= sends the
  host's current time and then =M=.

Between syncs the clock runs off the Pico's crystal-driven microsecond timer,
which drifts by at most a few seconds a day.

The firmware keeps UTC and converts it to local time itself: a fixed offset
(=-DCLOCK_UTC_OFFSET_MIN=, default 60 for CET) plus one hour during EU summer
time (last Sunday of March to last Sunday of October, at 01:00 UTC). Disable
the summer time rule with =-DCLOCK_EU_DST=0=.
